## 2. 폴더 구조

```
security/
├── threat-model/          자산, 데이터 흐름(L-1~L-6), 신뢰 경계, 위협 목록, 보안 요구사항
├── attack-scenarios/
│   ├── scenarios.yaml     공격·정상 시나리오셋 (시트 「시나리오」 C와 같은 ID)
│   └── fixtures/          공격 행을 넣은 가상 CSV·엑셀 (실제 개인정보 금지)
├── scripts/               공격 실행·결과 기록 스크립트
├── results/               방어율 기록 (1차·재검증)
└── reports/               취약점 리포트, 레드팀 결과서, 가드레일 정책·관제 리포트
```

## 3. 공격 유형 (시트 「시나리오」 C, 4유형 이상·유형별 2건 이상·정상 포함)

| 유형 | ID | 검증 주차 |
|---|---|---|
| ① 문서 접근 권한 우회 | A1-1, A1-2, A1-3 | W3-08 |
| ② 프롬프트 인젝션(직접·간접) | A2-1, A2-2, ATK-001~004 | W3-09 |
| ③ 민감정보·내부 문서 유출 | ATK-005~007, ATK-008 | W3-09 |
| ④ 승인·전달 우회 | A4-1 ~ A4-4 | W3-08 |
| 업로드 파일 | U-1, U-2 | W3-08 |
| 정상 | N-1, N-2 | 매회 |

기대 결과(상태코드·마스킹 여부)는 `attack-scenarios/scenarios.yaml`에 있습니다.
백엔드 담당(유시웅)과 상태코드를 맞출 때는 이 파일을 기준으로 합니다.

## 4. 가드레일 (W3-10, `backend/app/services/guardrails.py`)

| 단계 | 하는 일 |
|---|---|
| 입력 | '추가 요청'의 인젝션 패턴 검사, LLM 호출 전 개인정보 마스킹(전화·주민·카드·계좌·API 키 형태) |
| 출력 | LLM 응답 마스킹, 근거 상담ID가 실제 업로드에 있는지 확인 |
| 전달 | 상태가 `APPROVED`인지, 수신 주소가 허용 목록에 있는지 확인 |

정규식·패턴 목록을 바꾸는 PR은 유시웅이 리뷰합니다 (백엔드 테스트 영향).

## 5. 보안 이벤트 기록 기준 (S-7)

`security_events` 테이블: `user_id`(누가), `created_at`(언제), `target`(무엇에), `action`, `result`(허용/차단), `reason`.
차단·탐지 건수는 Grafana 보안 이벤트 패널로 보여 줍니다 (박준우와 지표 이름 맞추기).

## 6. 반드시 지킬 것

- 개발 DB는 Supabase, 배포 DB는 RDS입니다. A1-3(DB 직접 접속) 검증은 **배포 환경의 RDS**에서 합니다. 개발 Supabase 테이블에 RLS가 켜져 있는지도 1차 점검(W2-11)에서 확인합니다.
- 상담 내용이 외부 LLM 업체 3곳(Claude·Gemini·Groq)으로 나가므로, 마스킹(AD-4)이 세 업체 모두에 적용되는지 확인합니다. 업체별 데이터 이용 조건(무료 사용량 포함)도 위협 모델에 적습니다.
- 공격은 **우리 팀 개발·시연 환경에만** 실행합니다. 다른 팀·외부 서비스 대상 금지.
- fixtures에는 **가상 데이터만** 넣습니다. 실제 전화번호·카드번호처럼 보이는 값도 테스트용 형식(예: 010-0000-0000)으로 만듭니다.
- 공격 정답표·기대 결과는 저장소의 `security/`에만 둡니다. DB·프론트에 넣지 않습니다.
- 발견한 취약점은 GitHub 이슈(「보안 취약점」 템플릿)로 등록하고 담당자를 지정합니다. 심각도가 높은 내용은 공개 이슈에 재현 코드를 다 쓰지 말고 팀 채널로 공유합니다.
- 재검증(S-6)은 1차와 **같은 시나리오셋**으로 합니다. scenarios.yaml을 바꾸면 버전을 남깁니다.
